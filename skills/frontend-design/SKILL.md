# Frontend Design — IA and Semantic Integration

**Owner:** task and information structure, semantic/authority mapping, and evidence-calibrated UX. Livingware's generic engineering workflow owns implementation; Impeccable owns visual craft. Do not load both merely because a file is frontend code.

## Entry and routing

- **Enter:** a new or materially changed user task, information hierarchy, navigation/recovery contract, cross-panel coordination, source/evidence relation, or disputed IA. Use [IA-Before-UI](../../docs/ia-before-ui.md) before material visual decisions or implementation; record `GO_FOR_UI | REVISE_IA | NOT_APPLICABLE` only in the existing task/plan/spec.
- **Reuse and skip:** for an IA-preserving bug fix or visual refinement, reuse the existing accepted task/IA and design authority instead of reconstructing them. Pure routing/data fixes do not need Impeccable; an explicitly requested Impeccable command for visual work can enter that skill directly.
- **Conditional craft handoff:** select `impeccable` only for a concrete visual, interaction-craft, typography, accessibility critique, motion, responsive composition or polish need. Its [shape](../impeccable/reference/shape.md) already owns generic audience/goal/material/states brief discovery; its [new-work](../impeccable/reference/new-work.md) and [operate](../impeccable/reference/operate.md) own general visual-world and product UI craft. Reuse the settled brief/IA; do not repeat interviews, context setup or broad screenshots.
- **Independent authority:** the product's declared `DESIGN.md` / design-spec, actual incumbent design system and task/semantic contracts override generic Impeccable preferences. Missing `DESIGN.md` is not permission to replace an established visual identity.

## IA obligations not replaced by Impeccable

Apply the relevant portions of [IA-Before-UI](../../docs/ia-before-ui.md), with the smallest current-task record:

1. **Job and bounded user benefit:** identify the actual JTBD, first useful result, real task context, and observed versus inferred value. Preserve MVL Law 1: normal low-risk exploration and reversible actions are default-pass.
2. **Cognitive-work allocation:** place remembering, finding, routine comparing/calculating, safe defaulting, and recovery on the system when feasible. Preserve necessary user judgment and explicit authority; use Fix → Infer → Recommend → Ask. Do not infer success or cognitive relief from a pretty screenshot.
3. **Canonical semantic owners:** for each task, workspace, source, selection, result and consequential action, name the existing owner and version/scope. Do not create competing controls or infer authority from UI state; separate selecting/navigating from saving, executing, admitting and activating.
4. **Evidence continuity when applicable:** bind overview/result, judgment/process, and precise source/evidence through owner-issued relationships and exact object/version/occurrence IDs. Preserve reverse navigation, return/recovery, missing-link/UNKNOWN behavior and stale-response isolation. Select [IA/UX principles](references/ia-ux-principles.md) and [review checks](references/ia-ux-checklist.md) only for materially affected relations (including P06/C41–C46).
5. **Task-path acceptance:** verify affected scope/identity, task state, recovery, keyboard/compact access and evidence relationships using proportionate deterministic/real-browser checks. Human comprehension or reduced cognitive load remains unmeasured without actual human evidence.

For an established design system, inspect only the affected design authority, templates, tokens and components. For Semantier Asimov surfaces, conditionally read [Asimov alignment](references/asimov-alignment.md) and the current workbench/component showcases; do not load these for unrelated products.

## Exit and completion

- `GO_FOR_UI`: semantics and IA are settled; hand visual work to Impeccable only if craft is actually in scope, or continue the selected engineering workflow.
- `REVISE_IA`: a material task/owner/recovery ambiguity prevents correct UI design; resolve it through the existing owner without a new approval ritual.
- `NOT_APPLICABLE`: no material IA change; preserve the existing design and test only the affected implementation behavior.

A UI code change is complete when the relevant task path and design-system conformance are supported by current evidence. Apply existing Verification Impact Analysis / R0–R3; use one consolidated real-browser acceptance where required, reuse unchanged evidence, and do not run an automatic Impeccable critique or whole-product visual audit for a local change.
