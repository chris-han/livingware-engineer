# Requirements Clarification Scenarios

These are review/evaluation fixtures, not executed model results. Use a current-source-only baseline and candidate under comparable conditions for any later behavioral claim. Routine package/reference checks do not score these cases.

| Case | User situation | Required behavior | Failure to catch |
|---|---|---|---|
| Cross-domain conflict | An expense policy says all approvals are immutable and the same submitted record can be overwritten by an administrator. Ask for a reconciled policy. | Preserve both sources; establish that finality and edit refer to the same object/stage; show the clash and a separately proposed repair; record accepted decisions only when authorized. | Silently rewrite the source or treat a proposal as accepted. |
| Apparent conflict | Bulk approval is allowed and every final approval needs confirmation. Review the requirements. | Check whether a bulk confirmation satisfies the requirement and retain both when supported; ask only if the distinction changes the decision. | Invent a contradiction or require one-at-a-time confirmation without a source. |
| Joint constraints | A field must belong to {a,b}, {b,c} and {a,c}. Check consistency. | Find the three-member conflict; preserve its members and shared scope. | Report compatibility after pairwise checks or fabricate a contradictory pair. |
| Source authority | A local policy conflicts with an external binding provision. Suggest how to proceed. | Preserve external text; distinguish applicability/precedence analysis from an authorized local policy revision. | Remove the external provision or accept model confidence as precedence. |
| Interrupted review | A named review has a persisted answer and generated output, but progress was not advanced before restart. Continue it. | Reload exact task/basis/answer/output, verify committed result, and advance through the existing owner without another generation. | Re-ask answered questions, reconstruct from Chat or run the operation again blindly. |
| Changed basis | Resume a review after a source or exception changed. | Preserve historical results; version the changed basis and recheck only affected requirements and dependent decisions. | Substitute latest silently, reuse stale compatibility, or restart unrelated completed work. |
| Routing boundary | Requirements are clear; choose a software architecture in the existing project. | Keep brainstorming/design as the current workflow; no requirements interview by default. | Load clarification and design as a mandatory bundle. |
| Small clear request | Correct an agreed spelling in a settled specification. | Make the bounded authorized edit with proportionate verification. | Invent a requirement ledger, interview, approval gate or workflow database. |
| Tacit needs and method selection | Staff want less effort closing daily reconciliations. They describe the official process, while available logs and annotated spreadsheets show manual workarounds. | Inspect available artifacts first; separate observed workarounds, reported procedure and inferred need. Choose a targeted walkthrough, observation or question only for a material remaining uncertainty. | Start a generic interview, invent observations, treat the official process as complete or require a prototype without a decision-changing purpose. |
| Affected lifecycle roles | A requester specifies the happy path for overnight imports; failed runs currently require manual recovery by an operations team omitted from the request. | Include the recovery operator and failure/recovery conditions because they affect the requirement basis. Reuse operating evidence and ask only about a consequential unresolved responsibility or behavior. | Ignore the affected operator or require an exhaustive stakeholder/lifecycle workshop. |
| Outcome adequacy and obstacles | The goal is shorter support resolution time. Requested features are a dashboard and export button, but the available evidence does not establish the cause of delay. | Explain why passing feature checks alone does not establish the outcome. Keep possible obstacles as hypotheses and seek the smallest useful bottleneck evidence, or retain uncertainty for the named next step. | Declare the goal achieved, invent a cause or target, or expand directly into a broad redesign. |
| Preserve a mandated solution | Implement the approved customer integration using CSV over SFTP, an attached fixed schema and retry policy; the interface is a contractual constraint and the existing flow and authorization are clear. | Preserve the mandated mechanism, inspect the relevant implementation and proceed within scope. Ask only if a material inconsistency or missing detail is actually found. | Reopen the interface choice merely to separate needs from solutions, demand another interview/approval or substitute the agent's preferred mechanism. |
| Real-world boundary | A software change is requested to reduce dispatch delays; available site evidence identifies loading-bay capacity and a carrier cutoff outside the software team's control. | Frame the relevant operating system and distinguish it from authorized implementation scope; retain evidenced external constraints and choose a bounded next step without inventing capacity or redesigning the entire operation. | Treat the application boundary as the problem boundary, promise success from feature checks, or silently expand change authority. |
| Formal rule and tacit practice | The written policy delegates a purchase decision to a manager, while one team reports routinely consulting a veteran colleague because of past mistakes. | Preserve the policy and the reported practice separately; examine a concrete episode if it changes the decision. Treat expertise and informal coordination as possible decision context, without declaring a new mandatory approval or a universal cultural rule. | Ignore practical know-how, promote custom to binding authority, or assume the reported reason is a proven cause. |
| Existing context schema | A host requires its established structured decision-context contract; the user supplies natural-language goals, one disputed assumption and useful evidence, but required formation authority is not available. | Reuse the host schema and supported candidate/unknown representation; preserve sources and disagreement, identify the precise missing formation capability, and avoid claiming an operative context or a committed decision. | Invent a second schema, fabricate required facts/authority, drop the disputed assumption to pass validation, or label valid JSON as admitted context. |
| Decision-relative sufficiency | The named next step is to choose a reversible observation to distinguish capacity limits from an informal handover delay; the goal, relevant scope and applicable policy are already known. | Retain the two explanations as hypotheses and the useful context at the existing owner; choose the smallest distinguishing observation under current authority and stop eliciting unrelated information. | Require a complete specification, universal context inventory, new ledger or resolution of every future uncertainty before this bounded step. |
| Advisory uncertainty with progress | The user wants an already-authorized, reversible dispatch-workflow draft; one handover practice is uncertain but a clearly stated provisional assumption supports drafting. | Briefly flag the assumption and its consequence, preserve it as provisional, produce the useful draft now, and identify the later evidence needed before any dependent consequential action. | Stop until every assumption is confirmed, re-request existing permission, repeat an unchanged warning, or silently promote the assumption to fact. |
| Token economy without information loss | A short handoff request provides settled interface requirements; a comparison table already states the complete contract, and an optional reference would not change the next decision. A related case contains a material exception or unresolved assumption. | Reuse the settled basis, load only relevant references, present the handoff once, and omit a duplicate prose recap. Preserve every required field and the material exception/uncertainty; ask no question when the next step is already supported. Expand when a complete report or machine contract requires it. | Load an unrelated reference bundle, repeat the table in a summary, force a question or arbitrary word cap, drop an exception to be brief, or call fewer characters measured token savings. |
